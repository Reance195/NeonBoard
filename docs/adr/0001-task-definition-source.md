# 0001. 任务定义单源：台账管开发卡，board.db 管个人卡

- 状态：accepted
- 日期：2026-10-27
- 关联：`docs/product-design.md` §2 / §3、`docs/task-card.md`、`docs/board-ledger.json`、`src/TaskExec.*`、[R6 派发器计划](../archive/r6-dispatcher-plan.md)

## 背景

派发器需要卡片带 `goal` / `acceptance` / `scope` / `cwd` 才能执行，而当前这些字段在**两个地方**都可能有：

| 位置 | 谁在写 | 特点 |
| --- | --- | --- |
| `docs/board-ledger.json` 的 `cards[<短号>]` | 维护者（人） | 进 git、可评审、CI 可校验、随分支合并演进 |
| `board.db` 的 `task_exec` 行 | 看板应用（人随手改） | 运行时高频写、不能进 git、随机器走 |

两边都能定义 acceptance/scope，就会漂移。已经出现的具体症状：

- 台账 55 张卡里只有 6 张填了 `acceptance` / `scope`，其余卡在 CI 里等于没有边界（棘轮豁免）；
- 台账 `baseline` 里 R4-09 仍是 `todo`（实际已完成），导致「已完成卡不可重新领用」的闸门事实上失效；
- R4-08 的 `note` 写着「待做 Ninja / sccache」，而 CI 早已启用；
- 同一张卡的验收标准，在台账、卡片 note、README 里各有一份措辞不同的版本。

派发器上线后这个问题会放大：**执行按哪一份定义跑？** 若答案是「最后改的那份」，等于没有事实源。

## 决策

按**卡片类型**划分事实源，不做单一存储：

1. **开发卡**（路线图任务，短号形如 `R6-04` / `M19`）以 `docs/board-ledger.json` 为唯一事实源。
   执行定义写进 `cards[<短号>]` 的 `acceptance` / `scope` / `depends`，随分支提交、随合并评审。
2. **个人卡**（用户自己录的任务）以 `board.db` 的 `task_exec` 为唯一事实源，随手改，不进 git。
3. 两者用卡片 `code`（短号）关联，只允许**台账 → board.db 的单向导入**（R6-09）：
   - 以 `code` 找到 board.db 里标题内嵌该短号的任务；
   - **只补空值，不覆盖非空值**；冲突（两边都有且不同）只报告，交人决定；
   - 台账里有、board.db 里没有对应任务 → 报「未建卡」，**不自动建卡**；
   - 导入幂等：连续导入两次，第二次零变更。
4. **反向（board.db → 台账）永远需要人确认后提交**：可以在 UI 里生成一段可复制的 JSON / 一个提交草稿，
   但**不提供**「一键写入台账」按钮，agent 也不得自动改 `cards` / `baseline`。

## 理由

- **两类卡的生命周期完全不同**。开发卡要评审、要追溯「谁改了这个 scope」，天然属于 git；
  个人卡是「我自己今天要做的事」，让它进 git 等于给个人使用加一道提交流程，会直接劝退用户。
- **单向导入足够解决重复劳动**。开发卡的 acceptance/scope 只在台账写一次，导入后 board.db 里有副本用于执行；
  副本过期时再导入一次即可，不会反向污染 git。
- **保留有意的摩擦**。`AGENTS.md` 条款 6 已经规定 agent 不得改台账 `cards` / `baseline`——
  因为那等于 agent 给自己授权扩大 scope。单向导入把这条约束从「纪律」落到「没有代码路径」。

## 后果

**正面**

- 每张卡只有一个「定义事实源」，执行、评审、CI 校验读的是同一份；
- 开发卡的定义可评审、可回滚（git），个人卡保持零摩擦；
- agent 不可能通过执行链路自授权改边界。

**负面**

- 同一份定义在 board.db 里仍会有一份副本（用于执行），副本会过期；
- 需要一次显式导入动作（或启动时提示「有 N 张卡的定义比台账旧」）；
- 台账的 `note` 首段被借用为 `goal`，写法上要自觉保持「一句话说清目标」，否则 goal 会变成长篇背景。

**我们接受这些代价**，因为过期副本只会导致「按旧定义执行」，而人工确认后重新导入即可恢复；
反过来让 board.db 成为事实源，则会让「agent 改了自己的验收标准」变成可发生的事，代价大得多。

## 备选方案

| 方案 | 为什么不选 |
| --- | --- |
| 全部存 `board.db` | 定义不可评审、不可回滚；agent 可直接改自己的 scope；换机器就丢 |
| 全部存 `board-ledger.json` | 个人卡要提交才能改，用户不会接受；台账会被个人任务淹没 |
| 双向自动同步 | 冲突策略无法自动判定（谁赢都可能错）；且给了 board.db 一条写入 git 的路径，等于绕过评审 |
| 只做「台账是唯一源」，个人卡不允许执行 | 与产品定位冲突：个人用户录的卡才是主场景 |

## 验证方式

- R6-09 单测：新导入 3 张卡 → 变更 3；再导一次 → 0；已有不同值 → 报告冲突且不覆盖；未建卡 → 只报告；
- `python scripts/derive_board_status.py --check` 通过（台账状态与 git 历史一致）；
- 代码审查：仓库内不存在 `board.db → board-ledger.json` 的写入路径（grep `board-ledger` 只应出现在读取侧与脚本）；
- 人工：执行一张开发卡，其 `acceptance` 与台账里写的完全一致。
