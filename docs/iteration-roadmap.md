# NeonBoard 迭代路线图（炫酷优先）

> 数据基准：GitHub star 快照 2026-10-21；竞品功能与本仓库代码现状均已核对。
> 定位：**单文件、离线、开机即用的赛博霓虹个人工作台**。

## 0. 三条不可妥协的原则

1. **第一眼惊艳** —— 启动画面、主界面、托盘、弹窗，任何一屏截图都必须能直接当壁纸发出去。
2. **每一帧顺滑** —— 炫酷的反面是卡顿。当前启动 9696 ms / 56 fps 是硬伤，掉帧的霓虹不如普通界面。
3. **每次操作有反馈** —— 拖动、勾选、删除、撤销、提醒，都要有动效 + 声音/光效，且动效不阻塞操作（≤ 250 ms）。

在此之上，功能是底座：**不炫的功能也要有，否则用两天就卸载；不酷的功能再好也留不住人。**
本路线图把“炫酷”拆成三层推进：

```text
P0 炫酷地基（不修，炫不起来）
   ├─ 启动性能 9.7s → <1.5s
   ├─ 帧率与画质分级（60fps 保底）
   ├─ 动效基线 + 组件拆分
   └─ 主题引擎 v1（多套配色 + 强调色）

P0.5 日常底座（不补，做不了主力工具）
   ├─ 提醒 / 逾期 / 重复任务
   ├─ 子任务与卡片详情
   ├─ 导入导出 + 自动备份
   ├─ 快速录入解析 + 命令面板
   ├─ 列内精确插位 + 通用撤销
   └─ 首启动引导（三步说明 + 示例卡 + 任务模板）

P1 炫酷记忆点（差异化，别人抄不走）
   ├─ Shader 场景化（列状态 / 专注模式 / 脉冲）
   ├─ 统计可视化（热力图、连续天数、吞吐曲线）
   ├─ 专注模式 + 番茄钟（官方插件）
   ├─ 主题包市场
   └─ 拖拽手感（抬升、磁吸、落点涟漪、光轨）

P2 炫酷生态
   ├─ 插件平台 2.0（热重载 / 设置页 / 命令 / 事件）
   ├─ 动态托盘 + 窗口边缘辉光提醒
   └─ 启动序列动画 + 可选音效
```

## 3. P0 炫酷地基

### 3.1 启动性能：先纠正认知，再谈优化（R0 已实测 + 已瘦身）

> **状态：诊断完成，QML 树瘦身已完成。** 原判断「冷启动 9.7 s 是设计缺陷」**不成立**——它是**首次运行 / 冷页缓存**的一次性成本。

R0 诊断手段（已落地的工具，保留复用）：

| 手段 | 位置 | 作用 |
| --- | --- | --- |
| 分段打点 | `src/main.cpp` 的 `BOOT db / engine / qml / loaded / attached / shown` + 新增 `BOOT firstframe` | 定位每一段耗时 |
| `--smoke` 旁路单实例 | `src/main.cpp` | 诊断标志在应用运行时也可用（原先被 `QLocalServer` 锁挡掉） |
| `--benchload [minimal\|controls\|button]` | `src/main.cpp` | 分档加载探针 QML，量化各部分开销 |
| `NEONBOARD_NO_BG=1` | `src/main.cpp` → `Main.qml` | A/B 关掉动态背景，区分「背景 shader」与「其余」 |
| `UiSettings` | `src/UiSettings.{h,cpp}` | 外观/画质持久化（QML 侧 `QtCore` 的 `Settings` 在本机不可用） |

实测结论（2026-10-21，Release 构建）：

| 场景 | 结果 |
| --- | --- |
| 首次运行（全新用户，磁盘/页缓存全冷） | `BOOT loaded` 4.8 s，`BOOT shown` 5.9 s，指标 6841 ms |
| 热启动（连续 5 次） | **1.23 – 1.39 s 稳定**，fps 60.0，内存 199–204 MB |
| 瓶颈段 | `engine → loaded`（QML 树构建）**0.80 – 0.94 s**，是最大头 |
| `--benchload` | 最小 QML 仅 112–166 ms（含 Qt Quick 初始化 + 图形设备创建）；`import QtQuick.Controls` 仅多 ~50 ms |
| 背景 shader | **不是**启动瓶颈（关掉后启动耗时无明显变化），但它是 fps 指标的来源 |

#### 已完成：重型面板改为 Loader 按需加载（R0 收官项）

首帧根本用不到的界面，之前却在启动时全部构造。已按需化：

| 面板 | 之前 | 现在 | 位置 |
| --- | --- | --- | --- |
| 设置面板 | `Main.qml` 内联 Rectangle（遮罩 + 居中卡片） | `Loader` 懒加载 `components/SettingsPanel.qml` | 首次「设置」/ `Ctrl+,` 才构造 |
| 插件面板 | `Main.qml` 内联 Rectangle | `Loader` 懒加载 `components/PluginPanel.qml` | 首次点插件才构造，插件 QML 再晚一层 |
| 外观面板 | `ThemePicker.qml` 内联（含 `MultiEffect` 投影 + 6 行预设） | `Loader` 懒加载 `components/AppearancePanel.qml` | 首次点外观按钮才构造 |

要点与坑：

- **Loader 会把自身尺寸强加给被加载项**（`widthValid/heightValid`）→ 定位与尺寸一律由 `Loader` 负责，被加载组件内部不再写 `width/height/anchors`。
  外观面板最初「按钮高亮但面板不显示」，根因就是 `Loader` 只锚定了 `top/right` 而高度为 0 → 面板被压成 0 高；改为 `height: item ? item.implicitHeight : 0` 后正常。
- 外观面板里的 `Layout.fillWidth` 用在普通 `Row` 里会报「不存在的附加对象」→ 整棵 `body` 改为 `ColumnLayout` 体系。
- 新增 `--appearance` 启动参数，用于无鼠标环境下直接打开外观面板做验证。

A/B 实测（`NEONBOARD_NO_BG=1` 关背景，用**进程 CPU 时间**与 `engine→loaded` 树构建耗时衡量，墙钟噪声过大不可用）：

| 版本 | 树构建 `engine→loaded`（avg / min） | 启动总 CPU（avg / min） |
| --- | --- | --- |
| 基线（面板常驻构造） | 1694–2024 ms / 1270 ms | 2380–2552 ms / 1875 ms |
| 按需加载后 | **1448–1851 ms / 781 ms** | **2260–2583 ms / 1344 ms** |

三轮交错 A/B（6 / 12 / 10 轮，其中一轮刻意反序以排除顺序偏差）结论一致：**树构建耗时下降约 250–490 ms（-15% ~ -27%），启动总 CPU 下降约 70–300 ms**，达成「QML 树瘦身 200–400 ms」目标。

剩余可做（优先级从高到低）：

| 子项 | 做法 | 预期 | 状态 |
| --- | --- | --- | --- |
| QML 树瘦身 | 面板类（设置 / 插件 / 外观）改 `Loader` 按需加载 | 200–400 ms | **已完成（实测 -250 ~ -490 ms）** |
| 数据库 | `Database.cpp` 在 UI 线程同步建表/迁移，改为独立线程 + 延后首帧 | 数十 ms | 待做 |
| 插件扫描 | `PluginLoader` 扫描目录在主线程，改为后台扫描，首帧后再注入侧栏 | 数十 ms | 待做（实测当前仅 2–8 ms，优先级下调） |
| 字体 | `Cascadia Code` 缺失时的回退字体加载可能阻塞首帧 | 数十 ms | 待做 |
| Shader 预热 | `.qsb` 首次链接可在 Splash 阶段预热（当前冷态 BOOT shown 比热态多 1–2 s） | 可能秒级 | 待做 |

**验收**：热启动 < 1.5 s（**已达成：1.23–1.39 s**）；首次运行 < 3 s（待优化）；指标面板保留可见（这本身也是炫酷元素）。

> **2026-10-29 立卡**：上表「剩余可做」四项（数据库 / Shader 预热 / 字体 / 插件扫描）的收口已由台账卡片

### 3.2 帧率与画质分级（已落地三档）

**已实现**：

- `quality` 三档（低 / 中 / 高），由外观面板直接切换，持久化在 `UiSettings`。
- Shader 分支：`shaders/neon.frag` 新增 `uQuality`，低档跳过星星与扫描线，高档额外叠加颗粒。
- 低档时 `NeonBackground` 的推进间隔从 16 ms 放宽到 33 ms（≈30 fps），明显省电。
- 窗口失焦 / 最小化时暂停背景动画（`active: window.active`）。

**剩余**：

- 背景改用 `FrameAnimation`（Qt 6.4+）或 `QQuickWindow::beforeRendering` 推进 `iTime`，替掉 `NeonBackground.qml` 里的 16 ms `Timer`（定时器抖动 + 常驻 CPU）。
- Shader 降采样：低档用 0.5 倍渲染纹理再放大（`ShaderEffect.sourceSize`）。
- 辉光用 `MultiEffect` 按需启用：仅 hover/激活卡片开 `layer.enabled`，避免每张卡都做全屏模糊。
- 主题与画质解耦：主题包（`theme.json`）可自带推荐画质档。

**验收**：1920×1080 常态 60 fps（**已达成：热启动 fps 60.0**）；动画期间无掉帧；低档在集显上 ≥50 fps；纯 CPU 占用 <3%。

### 3.4 主题引擎 v1 —— **已完成**

**实际实现**：

- `qml/theme/Theme.qml`（QML Singleton）：颜色令牌（bg / text / muted / cyan / magenta / violet / success / warning / danger + 派生的 border / panel / card / input / accentSoft / elevated / ghost 等），每个令牌带 `Behavior on color`，切换时**全应用渐变**。
- `qml/theme/Motion.qml`（QML Singleton）：动效时长与缓动令牌 + 减弱动效开关。
- **6 套预设**（实际名称）：霓虹青（默认）/ 赛博紫 / 落日橙 / 深海蓝 / 森野绿 / 极夜灰。每套含 bg / text / muted / 三主色 / 成功 / 警告 / 危险色。
- **背景联动**：`shaders/neon.frag` 新增 `uBase / uPrimary / uSecondary / uAccent / uQuality` uniform，霓虹背景随主题一起渐变（这是「炫酷」的关键一环）。
- **入口**：标题栏右侧三色圆点按钮 → 外观面板（预设列表 + 画质三档 + 减弱动效），`MultiEffect` 真投影 + 逐行错峰渐入。
- **持久化**：C++ 侧 `src/UiSettings.{h,cpp}`（QSettings，`appearance/` 段）。**注意**：QML 侧 `import QtCore` 的 `Settings` 在本机不可用（`QtCore` 是磁盘动态插件且无 CMake 目标），故走 C++ 上下文属性 `uiSettings`。

### 3.5 看板阶段视图 + 路线图双向绑定 —— **已完成**

**问题诊断（来自实际使用反馈：「为啥面板上还没结束」）**

看板本身有两层缺陷，都不是「忘了勾」，而是设计缺口：

1. **同步是单向人工镜像**：`progress.json → board.db` 靠人跑脚本，git 提交不触发；应用里改卡也不回写；两侧不一致时系统没有自我纠正机制。
2. **看板表达能力不足**：卡片平铺，没有「阶段」维度。R0 的 10 张卡散在「已办结」列，R1/R2/R3 平铺在「待办」列，18 张 `#Mxx` 与 9 张粗卡混在一起、标签同为 R3 —— 数据里其实有阶段信息（标签首位），但界面没有聚合视图，「R0 是否收口」根本看不出来。

**A —— 阶段维度（表达力）**

- `TaskModel::stageStats()`：按里程碑聚合 `{total, done, doing, todo}`；阶段由**首个标签**判定（`^R\d+$` → R0..R3，否则 OTHER）。
- `TaskFilterModel` 新增 `stage` 属性，看板三列按阶段过滤。
- `qml/components/StageBar.qml`：看板顶部的里程碑进度条 ——「全部」+ 各阶段 chip（阶段名 / ✓ 完成标记 / `done/total` / 细进度条），点击即按阶段过滤；不同阶段不同强调色（R0 青 / R1 紫 / R2 品红 / 其他绿）。
- `--stage R0` 可在启动时直接进入某个阶段视图（便于脚本化验收）。

**B —— 自动绑定（事实源）**

- **快照格式 v2**：仓库 `progress.json` 改为 `{version, updated, items[]}`，每条含看板 UUID 作 id、完整字段与 epoch 时间戳（`createdAt` / `updatedAt` / `completedAt` / `orderKey` / `stage` / `deleted`）。
- **`src/RoadmapSync.{h,cpp}`**：应用侧读 / 写快照。路径解析优先级：环境变量 `NEONBOARD_ROADMAP` > ini `[roadmap]/path` > 从 exe 目录向上探测含 `.git` 与 `progress.json` 的仓库根。
- **三个触发点**：
  - 启动即导入（文件 → 看板）；
  - 每 15 秒轮询文件 mtime，变了就导入；
  - 看板侧改动 1.5 秒防抖后自动写回文件（看板 → 文件），内容无实质变化时**不写盘**，避免污染 git diff。
- **合并规则**（避免两侧互相覆盖）：
  - 运行中的进程持有基线，能识别「文件被外部改过」→ 这类条目一律以文件为准（不丢人工修改）；
  - 没有基线的冷启动 / CLI 则退化为「`updatedAt` 大者胜」，旧文件不会覆盖看板里的新改动；
  - 文件里有、看板里没有的条目写 `deleted: true`，导入时删除对应卡片。
- **git 钩子**：新增 `.githooks/post-commit`，提交若改到 `progress.json` 且应用未在运行，就用 CLI 把快照灌进看板；应用在运行则由它自己轮询接管。
- **可见性**：进度条右侧常驻同步状态（已连接 / 已对齐 / N 条外部改动），日志同步打印 `Roadmap: synced ...`。

> 手工改 `progress.json` 时请同步抬高该条目的 `updatedAt`，否则会以看板版本为准。

### 3.6 看板状态派生与一致性闸门 —— **已完成（L2 + L3 + L4）**

**遗留缺陷（3.5 之后的复盘）**：3.5 解决了「文件 ↔ 看板」的双向同步（数据层可靠，`diffs=0` 可验证），
但**卡片状态仍然是人手写的** —— 交付一个需求就手改一次 `progress.json`。
代码交付是「代码事实」，卡片状态是「人工记账」，两套事实源没有约束，漂移必然发生。

实测已发现两处漂移：「R1 命令面板（Ctrl+K）」代码早已交付（提交 `9869f88`）但卡片仍是待办；
「R1 快速录入解析」（提交 `90bc259`）甚至没有对应卡片。

**L4 —— 治本：状态不再由人手写**

- **快照升 v3**：每张路线图卡片带 `code` 短号（`R0-01` / `R1-03` / `M01`），`status` 字段成为**派生产物**。
- **台账 `docs/board-ledger.json`**：卡片身份（短号 ↔ UUID ↔ 标题 ↔ 阶段）与初始状态的唯一人工入口。
- **派生器 `scripts/derive_board_status.py`**：
  - `status(code)` = git 历史里最后一次出现的 `#code=状态` 标记 → 没有则退回台账 `baseline` → 再没有则 `todo`；
  - `--write` 把派生结果写回快照，`--check` 只校验（不一致退出码 1）；
  - 快照里带但台账没登记的短号、提交信息里写错的路线图短号（`R0-01` / `M01` 形态）一律报错拦下；
  - 形如 `#T12` 的计划钩子短号不在台账范畴，只提示不拦截（两种 `#短号` 语义的边界见 [docs/board-sync.md](docs/board-sync.md)）。
- **`src/RoadmapSync`**：快照版本升 3，导入时把 `code` 写进 `meta` 表的 `board.codes`，导出时带回 `code`（短号不会在往返中丢失）。

**L2 —— 自动流转：状态来自代码事实**

交付需求时在提交信息里带上短号即可：

```text
feat(board): 支持列内精确插位 #R1-04=done
```

历史里的标记就是状态的唯一来源，人无需再碰 `progress.json`。

**L3 —— 一致性闸门：漂移无法进主干**

- **PR / 分支推送**：CI 跑 `derive_board_status.py --check`，快照与派生结果不一致 → **直接拦住合并**。
- **合并到 `main`**：CI 跑 `--write` 并自动提交回写（`ci(board): 自动回写看板状态`）；
  快照提交只改 `progress.json`，流水线用 `paths-ignore` 排除，不会自激循环。
- **特性分支完全不碰 `progress.json`** → 多代理并行零冲突（此前每次交付都要手工改快照，是冲突与漂移的共同源头）。

**净效果**：状态变更只有两条有据可查的路径 —— 提交信息里的 `#短号=状态`（代码事实），或台账里的显式声明；
不存在「悄悄改了快照」这条路径，派生器与 CI 会把不一致直接指出来。

`product-design.md` §5 / §7 早已规划好下一层：**多卡排队执行**（不是一次一张）与**角色链编排**

**范围**
- **执行队列**：FIFO 排队、UI 暂停 / 调序 / 跳过、并发默认 1（设置可到 2）、夜间批量模式

- **角色链 workflow（M4）**：`workflow` 从单步升级为角色步骤数组（§7），每步一个角色、一份交接物文件

  决策失败分支、收口写 summary；预设 `fix / feature / hotfix / docs / review / delivery`。
- **成本账**（开放问题 #6）：记录每 run 的耗时（先记耗时，token 后续），卡片可见「花了多少」。

**依赖**：R6 全量落地（R6-04 执行器 + R6-05 验收 + R6-06 面板；Triage = R6-07 / Loop = R6-08 已在 R6 内）。

**判断依据**：R4 之后治理链（需求 → 台账 → 领用 → 验证 → 结卡）已经完整，但**人对全局的认知**仍是散在五份文档里，

**范围**：看板内置「项目全景」浮层（顶部「全景」按钮 / `Ctrl+K` / `NeonBoard.exe --map`），四个页签——

详见 [project-map.md](project-map.md) §14。

**出口标准**：仓库结构改动（新增目录、脚本改名）后，面板不需要改代码就能跟上；跟不上的地方必须自己喊出来
（链路标红「缺 N 个文件」，体检给 warn/error），并由 `ctest -R tst_projectmap` 兜底。

**DX-02 测试可启动性（已落地 ✅）**：在没把 Qt `bin` 加进 `PATH` 的终端里直接跑 `ctest`，测试进程会在加载
`Qt6Core.dll` 处失败，Windows 弹「系统错误」硬错误框、进程卡在框上不退出，`ctest` 只能等到 `TIMEOUT 120s`
—— 表象是「测试卡死」，实际是根本没启动起来，而且每跑一轮就攒一批弹窗。现在 `neonboard_add_test` 给每个测试
加 `ENVIRONMENT_MODIFICATION`，把 `$<TARGET_FILE_DIR:Qt6::Core>` 前置进 `PATH`，换机器 / 换 Qt 版本自动跟随，
不写死 `C:/Qt` 路径。验收：`PATH` 不含 Qt bin 时 `ctest` 仍 13/13 通过且零弹窗。

**DX-03 一分支多卡（已落地 ✅）**：2026-10-28 合并 DX-01/DX-02 时暴露出两道闸门互相打架 ——
`git-done` 的领用闸门要求「一个分支只能领一张卡」，而 `task_gate push` 是**逐提交**校验
`refs/claims/<卡号>`；一条分支装两张卡时，第二张卡在分支上无处领用，只能把占位建在一次性分支上再释放，
属于绕行。同一根因还让领用提交排在实现提交之后（先写代码后领用），两道闸门都查不出这种方向倒置。
两条候选路线：claims 列表化（改动面小），或新增 `scripts/split-card.ps1` 从既有分支拆卡（更贴合原意）。
**选 A（claims 列表化）**，落地如下：

- **口径改为「逐短号持证」**：`check_claim_refs.py` 不再限制只领一张，而是要求分支历史里出现的
  **每个**领用短号都在服务端各有 `refs/claims/<短号>` 占位 —— 多领合法、缺证照拒，并给出补领指引。
  台账 `claims` 本来就是按短号存的字典，同分支多条登记指向同一 `branch`，派生器与
  `release-claims.py` 已按短号遍历，无需改动。
- **补领幂等**：`agent-init.ps1` 判「本卡是否已在本分支领过」，已领即跳过；否则每补领一次都会多出
  两条同卡号提交（实测踩过，正是这条把它暴露出来）。
- **方向倒置只告警**：某张卡的实现提交早于它的领用提交，闸门给提示但不阻断 —— 历史分支确实需要补领。
- **自测入 CI**：`python scripts/check_claim_refs.py --selftest`（7 例：短号提取 / 去重 /
  方向告警正反例 / 流程提交不误报 / 多卡口径），CI 每次跑。

实测（临时仓 + 真实 git refs）：两卡一分支只给一张建占位 → `exit 1` 并点名缺证的那张；
两张都建占位 → `exit 0`；实现早于领用 → 告警且放行；单卡分支 → `exit 0`。
遗留：主线台账暂无第二张可领的卡，所以「两卡合一分支真正合入」这一条只在临时仓验证过，
等下次真有并行卡时自然覆盖。详见台账 `DX-03`。

**DX-04 阶段条数据驱动（已落地 ✅）**：阶段条原先只渲染 `全部 / R0 / R1 / R2 / R3 / 其他`，但 `board.db` 里实际有
R4 14 张、R5 5 张（含 1 张待办）、R6 9 张（含 6 张待办）—— 这些阶段既不在 QML 写死的数组里，也不计入
「其他」（「其他」只收 `stageOf` 认不出 `R\d+` 的卡），于是 **28 张卡在界面上完全不可见**。
现在阶段集合与顺序改取 §9 行序（`ProjectMap::stageOrder()`），`stageOf` 放宽到任意短号前缀
（`R4-10` 这类卡号仍不算阶段），「其他」降级为可对账的兜底桶（其他 = 全部 − 已显示之和），
阶段条配色也改为按行序取色板。验收：`tst_boardcolumns` 两条 + `tst_projectmap` 一条，
`ctest` 14/14；`--selftest` / `--smoke` 均通过且日志无 QML 告警。
遗留：**已由 DX-08 关闭**（原「阶段条未监听 roadmap 文件，§9 新增行需重启应用才反映出来」）。
现在启动即 `ProjectMap::startWatching()` 监听 `docs/iteration-roadmap.md`，阶段条与面板共用
`projectMap.onChanged` 这份信号；实测改 §9 后 **0.77 s** 内阶段条自动跟随（含 700 ms 防抖），
§9 写坏时保留上次有效集合并告警一次、不崩溃，恢复后自动回到正确集合。

**DX-05 会话隔离硬门（已落地 ✅）**：宪章 §7.2 要求「一 agent 一 worktree 一分支」，机制也确实在
`agent-init` 的 `else` 分支（`git worktree add .worktrees/<agent>`）。但 2026-10-28 凌晨两个会话
同时把**仓库根目录**当开发区 —— `.worktrees/` 一个都没建，HEAD 被对方切走，工作区与 `.sandbox`
双双失去隔离。原因是 `-InPlace` 本意只用于「已是隔离检出」，在锚点区传它等于自我降级，而脚本不拦；
配套的 `agent-workspace.ps1` 占用登记是自愿的（`Status` 显示 `root: 空闲`，两边都没做）。
现在三道一起收口：

- **锚点区禁止 `-InPlace`**：`agent-init.ps1` 用 `git rev-parse --git-common-dir` / `--git-dir`
  判定锚点（两者相等），命中即 `exit 3` 并提示正确用法；确需在锚点动手必须显式 `-ForceAnchor`
  （顺带登记 `root` 占用）。检出里已留**他人**的 `.agent-env.ps1` 同样默认拒绝，同开关才可接管。
- **开工自动登记**：`agent-init.ps1` 成功后写 `worktree:<agent>`（原地模式写 `root`），目标已被占用
  直接 `exit 3`；`git-done.ps1` 合并成功后按当前 agent 身份自动 `Release`（身份不符拒绝）。
- **体检**：`agent-workspace.ps1 -Action Check` 核对锚点 in-place 环境 / 一分支双检出 /
  每个 worktree 独立 `.sandbox` / 登记与目录对账，硬冲突 `exit 3`。

验收（逐条实测）：

- 锚点区 `-InPlace` → `exit 3`，提示里给出 `-ForceAnchor`；`.worktrees/agent-gov` 内同命令 → `exit 0` ✅
- 锚点区 `-InPlace -ForceAnchor` → `exit 0`，`Status` 显示 `root` 已被当前 agent 占用 ✅
- `agent-init` 后 `Status` 显示 `worktree:agent-gov` 已登记；`Release` 后恢复「空闲」，他人 Release 被拒 ✅
- `Check` 在干净状态下 `exit 0`；`AGENTS.md` §7.2 已写明 `-InPlace` 合法前提与 `-ForceAnchor` 用途 ✅
- 改动的 `.ps1` 均保留 UTF-8 BOM，`check_script_hygiene.py` 通过 ✅

遗留：登记文件 `<git-common-dir>/agent-workspace.json` 仍是本机共享元数据（与 `.git` 同寿命），
跨机器/多 clone 不传递；`Check` 的僵尸登记只告警不自动回收（回收由人拍板，§7.10）。详见台账 `DX-05`。

**DX-06 代登记可审计（已落地 ✅）**：宪章正文第 1 条允许「维护者显式授权代登记」，并要求
提交信息用 `chore(board):`、body 记录授权来源与批次、且只能在锚点区执行。但 `task_gate.py`
原先只校验了**位置**（非 `.worktrees` 直接放行），没校验**内容**——于是例外条款退化成口头免责：
只要站在锚点区，谁都能以「已获授权」为名加任意卡，事后无从追溯。本会话自查即五例为证：
DX-01 塞进 `feat` 代码提交、DX-02 塞进 `chore(tests)`、DX-03~05 用错前缀且 body 无授权记录。
现在把提交信息本身变成审计凭证，锚点区改动台账**任务定义**（新增/删除卡、改 `id`/`title`/`stage`、
改 `baseline`）时三道内容校验缺一即拒，位置校验保持不变：

- 类型必须 `chore(board)` —— 用 `feat` / `docs` 等语义夹带走卡片会被拒；
- body 必须同时有 `授权：` 与 `批次：` 两行（各自后写授权来源 / 本批卡号）；
- 不得同时改动代码路径 —— 立卡与实现分开提交。

只改 `claims` 或卡片 `note` 不算代登记、无需凭证。判定只有一处实现（`task_gate.py` 的
`audit_problems` / `ledger_definition_changes`，`cmd_ledger` 与 `cmd_message` 共用），
自带可执行自测 `python scripts/task_gate.py selftest`（允许 2 / 拒绝 4，含混提交与缺审计行），
CI 每次跑。实测：`feat` 类型立卡 exit 1、缺 `批次：` 行 exit 1、定义变更+代码混提交 exit 1、
合规 `chore(board)` exit 0、只补 note exit 0。详见台账 `DX-06`。

**DX-07 结卡权自动化（已落地 ✅）**：`baseline=<短号> done` 是「拒绝重新领用」的唯一门
（条款 6），而它长期靠维护者**记得批量结** —— 一定漂。2026-10-29 就漂了：`DX-03` / `DX-05` /
`DX-06` 已按 `#<短号>=done` 交付并合入 main，baseline 仍停在 `todo`；`R5-06` 连条目都没有，
`--baseline-check` 报「漂移 3 项 / 缺项 1 项」。每漂一次，已交付的卡就能被再领一遍重做。

现在**合入即结**：`git-done.ps1` 在合并推送成功后调 `derive_board_status.py --close-cards`，
从 git 事实（最后一次 `#<短号>=` 标记）把 baseline 补成 `done`（缺条目的卡按标记补 `done` / `todo`，
绝不把未交付的卡误结），作为独立的 `chore(board): 结卡 <短号>` 提交快进补推；提交或补推失败
只回滚该提交、不阻断已完成的合并。**agent 手改 baseline 仍被拒** —— 自动结只由收尾步骤做，
提交体注明「自动来源」。`--baseline-check` 随之从「只报不改的待决项」降为**回归探针**。

顺带修掉 DX-06 留下的一个真死锁：它将代登记限定在锚点区，而锚点区停在 `main`、
`main` 禁止直接提交、§7.1 又禁止 agent 在锚点区切分支 —— 三条叠加后代登记**无处可执行**
（实测连拒三次）。改为凭内容而非位置：任何检出里给出 `chore(board)` + `授权：` + `批次：`
且不混代码即可代登记，`cmd_ledger`（`pre-commit`，拿不到提交信息）只做提前告知。

验收：`derive_board_status.py --selftest` 6 例（有标记则结 / 无标记不动 / 已结不重复 /
缺条目补 todo 而非 done / 幂等 / 不擅自重开）；实测批量结清 3 项漂移 + 1 项缺项后
`--baseline-check` 归零、复跑幂等、diff 只动 baseline；DX-07 自身经「开发区代登记 → 领用 →
实现 → 合并」全链路走通。详见台账 `DX-07`。
