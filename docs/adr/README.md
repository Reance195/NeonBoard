# 架构决策记录（ADR）

> 记录**已经定下来、并且会影响后续多个改动**的决策。不是设计文档，不重复实现细节；
> 一个决策一篇，写完就不再改（要改就新写一篇把旧的标 `superseded`）。

## 什么时候写

- 改动会影响两个以上的模块或两个以上的卡片；
- 改动涉及数据存储形态（表结构 / 文件格式 / 迁移）；
- 改动涉及安全边界或「谁有权做什么」；
- 团队里出现过两种以上合理方案，需要留下「为什么选这个」。

日常的字段增补、样式调整、文案修改不需要 ADR。

## 文件格式

- 路径：`docs/adr/NNNN-<kebab-case-标题>.md`，编号四位、递增、不复用；
- 标题：一句话说清决策本身（不是「关于 X 的讨论」）；
- 正文按下面的骨架写，**必须**有「决策」「后果」「备选方案」三节。

```markdown
# NNNN. <决策标题>

- 状态：proposed | accepted | superseded by NNNN | deprecated
- 日期：YYYY-MM-DD
- 关联：<设计文档 / 卡片短号 / 代码路径>

## 背景
是什么问题逼着做决定？现状有什么具体症状（最好带事实，而不是假设）。

## 决策
选了哪一个。用祈使句写清楚「做什么 / 不做什么」。

## 理由
为什么是这个。列关键权衡，别写套话。

## 后果
正面、负面都要写。负面的要写「我们接受它，因为……」或「后续由 X 处理」。

## 备选方案
认真考虑过但没选的方案，以及没选的原因。这一节是给未来的自己看的。

## 验证方式
怎么判断这个决策落地了（测试 / 命令 / 人工检查）。
```

## 约定

1. **已接受的 ADR 不修改**（拼写错误可以改）。结论变了就新写一篇，旧的在状态里写 `superseded by NNNN`。
2. ADR 与卡片的关系：ADR 讲**为什么这么定**，卡片讲**这一轮改什么、怎么验收**。卡片可以引用 ADR，ADR 不承诺排期。
3. 任何与本目录冲突的实现都算缺陷；发现冲突先改实现，或新写 ADR 推翻旧决策，**不允许**两边并存。
